# OMP workflow semantics (YAN-1170)

Target: ystack v6.1.0. How the generated `packages/omp/ycc` skills behave under oh-my-pi (OMP) in
interactive, print/JSON and RPC modes. Verified on omp 18.12.3 (upstream `53a0377d`). Evidence and
the pre-change audit: [feature spec](../research/yan-1170-omp-workflow-semantics/feature-spec.md).
Contract: [ADR 0002](adr/0002-omp-runtime-contract.md). Capability verdicts:
`ycc/skills/_shared/references/target-capability-matrix.md` (`SKILLS:omp`, `AGENTS:omp`,
`WORKTREE:omp`).

## Mode contract

| Mode                    | `ask` tool      | Async `task` jobs              | ycc behavior                                                                              |
| ----------------------- | --------------- | ------------------------------ | ----------------------------------------------------------------------------------------- |
| Interactive TUI (`omp`) | yes             | auto-deliver; `wait` collects  | Ask. `recommended` is a hint only; an opt-in `ask.timeout > 0` selects it.                |
| `--mode rpc-ui`         | yes (UI frames) | auto-deliver; `wait` collects  | Same as interactive.                                                                      |
| `-p`, `--mode json -p`  | no              | dropped if the turn ends first | Declared default or stop with a `rerun with <flag>` line; `wait` until every job settles. |
| `--mode rpc`            | no              | dropped if the turn ends first | Same as `-p`. Tools that need approval fail closed under `--no-ui`.                       |
| Subagents (any mode)    | no              | n/a                            | Never ask; return the choices to the parent.                                              |

Rules shared by every skill:

- **Questions.** `_shared/references/question-policy.md` defines six gate classes (`clarify`,
  `confirm-destructive`, `confirm-publish`, `choose-path`, `checkpoint`, `failure-recovery`).
  Destructive and publishing gates never auto-approve without the skill's explicit flag. A
  question tool is available only when it is in the current tool list.
- **Dispatch.** The OMP `standalone-dispatch.md` is generated from
  `scripts/omp_templates/standalone-dispatch.md` (§1-7) plus the canonical §8-10. Fan-out is one
  `task({context, tasks: [...]})` batch with `agent` (not `subagent_type`); with
  `task.batch=false`, one `task` call per agent in one message. ycc never sets `isolated`.
- **Background jobs.** Never end a turn with owned jobs running: headless OMP exits after the
  turn and drops pending async results (`AGENT_END awaitingAsyncWork: true`). Call `wait` until
  every job settles; read `agent://<id>` when the inline summary is truncated at 5000 chars. Use
  `read proc://<id>` to inspect and `write proc://<id>/kill` to cancel. Bash commands that run
  past 60 s auto-background; CI monitors pass a sufficient `timeout` or `wait` for the job.
- **Teams.** `--team` fails closed on OMP. `write agent://<id>` peer messaging is not a team
  lifecycle.
- **Worktrees.** Skill-managed worktrees live under `<repo-root>/.omp/worktrees/`. The generator
  rewrites the `worktree-paths.sh` default to `.omp`; the portable `agents` bundle resolves `.omp`
  from `OMPCODE=1`, which consumes the `CLAUDECODE=1` marker OMP also sets. OMP's own isolation
  and `omp worktree` use `~/.omp/wt`; ycc neither uses nor deletes it. `YCC_WORKTREE_ROOT`
  overrides the root everywhere.
